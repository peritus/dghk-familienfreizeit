# 20.4 — Workshops

Module id `workshops` · factory `workshops`

## 1. Purpose and boundary

Workshops records the occasion programme: time slots, the workshops offered in each,
their capacity and age bounds, who they are for, who leads them, and manual
cancellation. It owns live sign-up and interest participation. Ranked preferences and solver
placement belong to
[workshop rankings](20.5-workshop-rankings.md) and
[workshop assignment](20.6-workshop-assignment.md). A programme without assignment
is a valid occasion: the module alone provides a programme with live participation. Release behaviour
is defined by [release control](06-release-control.md), not by a separate module
visibility mechanism.

This document is the authoritative description of slots, workshops, audience,
leadership, and manual cancellation.

## 2. Dependencies

Requires: none. Enhances: [`room-inventory`](20.1-room-inventory.md) —
when selected, a workshop may be held in a room.

## 3. Parameters

```ts
type WorkshopsParams = {
  audience_tag: string | null        // workshop property restricting participation
  leader_tag: string | null          // person property naming a led workshop
  leaders_consume_capacity: boolean
  require_leader: boolean
  excluded_roles: readonly string[]
  audience_rules: Readonly<Record<string, readonly string[]>>
}
```

| Parameter | Default | Validation |
|---|---|---|
| `audience_tag` | `null` | fills the audience role (§6) |
| `leader_tag` | `null` | fills the leadership role (§6) |
| `leaders_consume_capacity` | `false` | `true` requires `leader_tag` |
| `require_leader` | `false` | `true` requires `leader_tag` |
| `excluded_roles` | `[]` | role values excluded from participation |
| `audience_rules` | `{}` | audience values mapped to eligible role values |

## 5. Events

### `SlotAdded` / `SlotUpdated`

```ts
{ slot_id: string, label: string, starts_at: string, ends_at: string, sort_key: number }
```

Folds to `label`, `starts-at`, and `ends-at`. *Invariant:* `starts_at < ends_at`.
Slots are processed in `sort_key`, then `id` order, which must be chronological.

### `WorkshopAdded` / `WorkshopUpdated`

```ts
{
  workshop_id: string,
  slot_id: string,
  title: string,
  description: string | null,
  participation: 'assigned' | 'sign-up' | 'interest',
  capacity: number | null,
  min_capacity: number,
  min_age: number | null,
  max_age: number | null,
  room_id: string | null,
  sort_key: number
}
```

Folds to `offered-in = slot_id`, `title`, `description`, `participation`, `capacity`,
`min-capacity`, `min-age`, `max-age`, and `held-in = room_id`. *Invariants:*
`assigned` requires integer capacity ≥ 0 and `0 ≤ min_capacity ≤ capacity`;
`sign-up` permits null (unlimited) or integer capacity ≥ 0 and requires
`min_capacity = 0`; `interest` requires null capacity and `min_capacity = 0`.
`min_age ≤ max_age` when both are set; `room_id` is
null unless `room-inventory` is selected, and otherwise names a live room.

### `WorkshopCancelled`

```ts
{ workshop_id: string, reason: string }
```

Manual cancellation by an organiser. It is distinct from under-subscription
cancellation, which [workshop assignment](20.6-workshop-assignment.md) derives on
every run and reports in the trace — that is not an event, because it would
re-derive itself anyway.

### `WorkshopReinstated`

```ts
{ workshop_id: string }
```

Undoes a manual cancellation.

All workshop setup events are organiser-only. Live participation uses ordinary
label events (§6), with own-family authorisation. Updates are full restatements.
Draft changes do not change the operational programme before communication; mode
and slot transitions follow [release control](06-release-control.md) §5.

```kdl
SlotAdded slot_id=slot_sat-morning label="Samstag Vormittag" starts_at="2027-05-01T08:00:00Z" ends_at="2027-05-01T10:30:00Z" sort_key=1
WorkshopAdded workshop_id=ws_toepfern slot_id=slot_sat-morning title="Töpfern" description=#null participation=assigned capacity=12 min_capacity=6 min_age=8 max_age=#null room_id=#null sort_key=1
LabelSet entity_id=ws_toepfern key=workshop-audience value=children strength=#null
LabelSet entity_id=per_anna key=leads-workshop value=ws_toepfern strength=#null
```

## 6. Labels and tag roles

Module-owned label keys, each owned for the entity kind named beside it:
`label`, `starts-at`, `ends-at` on `slot`; `offered-in`, `title`, `description`,
`participation`, `capacity`, `min-capacity`, `min-age`, `max-age`, `held-in`, and `cancelled-reason`
on `workshop`. All are set only by the module's events, and the same key stays
free on entity kinds this module does not own ([modules](20-modules.md) §3.1).

| Role | Parameter | Required tag shape |
|---|---|---|
| Audience | `audience_tag` | `property`, scope `workshop`, value `enumOf(…)`, cardinality exactly one, organiser-only |
| Leadership | `leader_tag` | `property`, scope `person`, value `ref('workshop')`, cardinality zero or more, organiser-only |

A workshop may have zero, one, or many leaders, and a person may lead many
workshops. Children may lead. Leadership is not participation: a leader is not
assigned to the workshop and does not consume capacity unless
`leaders_consume_capacity` is set. The audience controls who may participate; it
does not constrain who leads. When leaders consume capacity, effective participant
capacity deducts leaders; a leader already counted as an occupant consumes no second
place when joining. All assignment/admission paths use that same occupancy rule.
Audience and leadership labels themselves stay organiser-only; explicit programme
outputs may expose safe eligibility wording and leader display names for coordination,
not private raw labels or notes.

### Live participation labels

The module also owns `signed-up-for` and `interested-in` on `person`, with value
`ref('workshop')`, no strength, and cardinality zero or more across workshops. They
are writable through `LabelSet` and `LabelCleared`; unlike setup keys above they
have module-provided family controls. The profile supplies control copy/placement
without redefining these keys. Relations are resolved centrally, not in screens.

A family may change only its own non-withdrawn people's participation. Organisers
may act on their behalf. Admission uses the communicated programme and current
resolved participation ([release control](06-release-control.md) §5). Reject new
labels for hidden, cancelled or wrong-mode workshops, ineligible people, duplicate
sign-ups in one communicated slot, or a full sign-up workshop. Clearing an existing
label remains possible even when its target is cancelled or the person is now
ineligible. Repeating the same live label is idempotent and consumes no extra place.

Eligibility requires a non-withdrawn person, an allowed role, the configured audience
rule, age bounds at the occasion start, and applicable required resolver decisions.
The same policy serves assigned and live modes. Interest is non-binding and does
not reserve a slot or consume capacity. People can express interest in several
workshops in one slot. Shared views expose no interest names; a family's own choices
remain visible and organisers receive counts. Organiser source-label access remains
subject to the ordinary authenticated organiser boundary.

Capacity admission is first come first served by successful event sequence. Check
against the head derived for the request and append using its sequence guard. Two
requests for the last place cannot both succeed; the loser refreshes and retries
validation. There is no waiting list or solver displacement. Clear-and-set switches
can be one atomic label batch, validated in event order. Clearing first can free the
person's slot; a failed set rolls the whole batch back.

Capacity includes leaders when `leaders_consume_capacity`; count unique people so a
leader with a participation label is not counted twice. Unlimited capacity is null,
not a large sentinel. Lowering communicated capacity preserves the list and raises
`workshops.sign-up-over-capacity`; reject additions until effective occupancy is below
capacity. A later eligibility change retains the label and reports affected people
for explicit resolution. No automatic eviction or conversion occurs.

Cancelled workshops retain labels for history but admit no additions. Their sign-ups
are inactive for slot reservation and counts of active attendance; reinstatement
previews their return and must satisfy release consistency. A withdrawn person's
labels remain recorded but do not consume capacity. Replay checks admission against
the operational programme at each event, not against the final draft state. Later
capacity/eligibility changes do not retroactively invalidate a once-valid append.

## 7. Solver input and stages

The resolver exposes the draft programme for planning and the effective communicated
programme for live admission. Only non-manually-cancelled `assigned` workshops enter
the assignment candidate array. Sign-up and interest workshops never enter it.

```ts
type WorkshopsInput = {
  slots: readonly { id: string, starts_at: string, ends_at: string, sort_key: number }[]
  workshops: readonly {
    id: string
    slot_id: string
    capacity: number                 // effective participant capacity; leader policy in §6
    min_capacity: number
    min_age: number | null
    max_age: number | null
    audience: string | null
    leader_ids: readonly string[]    // sorted
    room_id: string | null
    sort_key: number
  }[]                                // sort: slot order, sort_key, id
  reserved_slots: readonly { person_id: string, slot_id: string }[]
                                      // active sign-ups; sort: person_id, slot order, slot_id
}
```

Reservations are derived from active sign-up labels and their communicated slots.
They are only availability facts; sign-up lists and interest counts are not solver
outputs. Slots needed to remove old allocations remain addressable even when they
have no draft assigned workshops. Stages: none of its own.

## 8. Rules and scoring

None.

## 9. Preflight checks

None in the solver. World-level diagnostics:

| Id | Severity | Fires when |
|---|---|---|
| `workshops.missing-leader` | warning | `require_leader` is set and a workshop has no leader |
| `workshops.leader-clash` | error | a person leads two workshops in one slot |
| `workshops.room-clash` | error | two workshops in overlapping slots are held in one room |
| `workshops.age-band-without-eligible` | warning | no person's age at the occasion start falls within a workshop's bounds |
| `workshops.sign-up-over-capacity` | warning | effective occupancy exceeds a communicated finite sign-up capacity |
| `workshops.participation-ineligible` | warning | an existing participant no longer meets effective eligibility |

These are world-level diagnostics over the complete resolved programme, including
self-organised workshops. They are not placed in the solver Plan. Release control
uses their subjects when checking prospective schedule and participation consistency;
its hard gates are defined there.

## 10. Output and diff

No plan section. `world.slots` and `world.workshops` expose draft and effective
programme accessors; a world-level participation summary exposes active sign-ups in
admission-sequence then person-id order, interest counts, and diagnostics. The
module contributes canonical programme scope content to release control (§1 there).
Live participation is not part of that content.

`diff` reports `workshop-cancelled`, `workshop-reinstated`, and `workshop-changed`
for programme changes, including mode, capacity and eligibility. Release control
selects the relevant scope differences and recipients. Live participation changes
appear in organiser coordination views, not as release backlog.

## 12. Tests

- Invariants on capacity, ages, and slot times, at append and replay.
- Leaders never count as participants unless `leaders_consume_capacity`.
- A room reference fails when `room-inventory` is not selected.
- Fixture contract: two slots, one children's and one adults' workshop, one child
  leader, plus assigned/sign-up/interest workshops, a finite last-place admission
  race, and a communicated capacity reduction.
- Communicated programme controls admission while draft changes remain held.
- Concurrent last-place requests cannot both succeed; duplicate labels consume once.
- Clear-and-set switching is atomic; failed admission preserves the original list.
- Capacity reduction never evicts; withdrawal/cancellation removes active occupancy.
- Mode changes never convert or revive lists; reinstatement validates restored occupancy.
- Interest accepts no capacity, reserves no slot and exposes no shared names.
- Shared eligibility works without the assignment module; replay uses each event's cut.

## 13. When not selected

No slots or workshops exist; workshop events fail replay; the workshop screen,
programme, and roster reports are absent; `workshop-rankings`,
`workshop-assignment`, and workshop links in `materials` are unavailable.
