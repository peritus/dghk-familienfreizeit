# 03 — Event model

This document defines the generic event envelope and lifecycle. Occasion profiles
may contribute event types through selected modules, but the append, replay,
validation, and fold rules are shared by every deployment.

This file lists the kernel write vocabulary. Modules contribute further event types,
each specified in its module document and registered by `defineModule`
([modules](20-modules.md) §3.1). Adding a kernel event type means adding to this file,
to `src/events/types.ts`, and to the fold; adding a module event type means adding to
the module specification and the module's `events.ts`. Nothing else.

Semantic setup events (`FamilyInvited`, `PersonAdded`, module events such as
`RoomAdded`)
are convenient command vocabulary. Their complete payloads are folded into
one typed entity identity and generic labels. Constraints and intrinsic facts
then use the same
`LabelSet` stream; no event type exists solely for a particular preference or
organiser override.

## Shape

```ts
type Event<T extends string, P> = {
  seq: number            // head + 1 at append; the primary key rejects a stale append
  at: string             // ISO-8601 UTC, assigned at append time
  actor: Actor
  type: T
  subject: string | null
  payload: P
}

type Actor = string      // the authenticated principal, always
```

## KDL event-log format

Development and test event logs may be authored as KDL documents. Each
top-level node represents one event: its name is the event type and its
properties are the payload fields.

```kdl
FamilyInvited family_id=fam_a email="family_a@example.com" display_name="The A's" locale="de"
PersonAdded person_id=per_peter family_id=fam_a given_name="Peter" family_name="A" birthdate=#null role=adult
```

The project accepts a restricted KDL profile: one event node per line, no
positional arguments, and no child blocks. Blank lines and comments are allowed.
The parser reports syntax errors with file and line locations, rejects duplicate
properties, and maps only known event properties. Semantic validation then uses
the ordinary event payload schemas and replay invariants; KDL does not define a
new event vocabulary.

For ordinary authored fixtures, the loader supplies deterministic envelope
metadata: file order becomes `seq`, `actor` is `fixture`, `at` is a fixed test
timestamp, and `subject` is null unless a fixture explicitly supplies it. Tests
that exercise historical ordering or envelope behavior may provide `seq`, `at`,
`actor`, and `subject` as reserved properties. The loader must reject conflicting
or duplicate envelope fields.

KDL is the canonical authored representation for development and test event
logs. JSON may still represent API messages, serialized event rows, canonical
hash inputs, and derived results.

Every payload has a zod schema in `src/events/types.ts`. The schema is used twice:
to validate on append, and to validate on replay. Validating on replay sounds
redundant and is not — it catches the case where a schema changed and old events
no longer parse, which is the moment you need to write a migration rather than
discover the problem in the solver.

## Rules for payloads

1. **Payloads carry values, not references to mutable state.** `PersonAdded`
   carries the birthdate. It does not carry "look up the birthdate from the
   import file". Replaying the log must not require anything but the log.

2. **Payloads are complete, not deltas.** `PersonUpdated` and ranked-preference
   events carry complete restatements. Deltas mean the
   fold has to merge, merging has ordering subtleties, and the audit trail
   becomes unreadable. A full restatement is a few extra bytes and total clarity.

3. **Ids are generated by the caller before appending**, so the payload can
   contain them and the fold never has to invent one.

4. **No event ever contains a secret.** No tokens, no hashes of tokens, no
   session ids.

Setup event payloads are complete command inputs, not a second data model. The
fold creates the typed entity identity and emits the payload's mutable
values as labels, under the kebab-case form of the field name (D18). For example,
`PersonAdded.given_name` and `birthdate` become the labels `given-name` and
`birthdate` on the new person, and `RoomAdded.room_type` becomes `room-type` on the
room. Occasion-specific config defines
which labels are legal and how the resolver uses them.

## Setup and identity

### `FamilyInvited`
```ts
{ family_id: string, email: string, display_name: string, locale: 'de' | 'en' }
```
Emitted by an organiser, once per family, during import or manual add. Creates the
family. Does not send the email — that is an operational side effect performed
after the append succeeds.

*Invariant:* email must be unique case-insensitively across all families and
must not be an allowlisted organiser address. Checked against the derived world
before append; the `seq` guard makes the check and the append atomic. The import
preview reports a duplicate as a row-level error rather than aborting the whole
import.

### `FamilyEmailChanged`
```ts
{ family_id: string, old_email: string, new_email: string }
```
Organiser only. Carries the old value so the history reads correctly without
replaying to that point.

*Consequence:* the old address stops resolving to this family on the next request,
so its sessions lose access without a cleanup step
([authentication](11-authentication.md) §3, rule 8).

### `PersonAdded`
```ts
{
  person_id: string, family_id: string,
  given_name: string, family_name: string,
  birthdate: string | null,
  role: string                  // values are validated by the active profile
}
```
Emitted by the family or by an allowlisted organiser. Folds to `member-of`,
`given-name`, `family-name`, `birthdate`, and `role`. Everything else about a person —
bed demand, accessibility, diet — is an ordinary label set by the module or profile
tag that owns it.

*Note on `role`:* it is stated, not derived from birthdate. A 17-year-old may be
registered as an adult by their family and that is their call. Modules use `role`
for role-based rules; no module turns role into a bed exception.

### `PersonUpdated`
```ts
{ person_id: string, /* full restatement of all mutable fields */ }
```

### `PersonWithdrawn`
```ts
{ person_id: string, reason: string | null }
```
Excludes the person from newly derived plans. Historical plans keep them.

## Labels and constraints

Families may set labels only on themselves or their own people. An allowlisted
organiser may set any domain label. The resolver validates both built-in labels and
custom matching definitions before append.

### `LabelSet`
```ts
{
  entity_id: string
  key: string
  value: string
  strength: 'required' | 'preferred' | null
}
```

This is the one event for intrinsic facts, preferences, capabilities, and organiser
decisions. Values may be scalar facts or stable entity ids. For example:

```ts
{ entity_id: 'per_42', key: 'needs', value: 'room-with-garden-view', strength: 'required' }
{ entity_id: 'rm_07', key: 'provides', value: 'room-with-garden-view', strength: null }
```

### `LabelCleared`
```ts
{ entity_id: string, key: string, value: string | null }
```

`value: null` clears every current value for the key. The original label event
remains in the log.

### `ConstraintDefined`
```ts
{
  key: string,
  label: string,
  description: string,
  operator: 'needs-provides' | 'excludes' | 'groups-with' | 'separates-from',
  needs_scopes: string[],
  provides_scopes: string[],
  strength: 'required' | 'preferred'
}
```

Defines a custom matching vocabulary. It contains no executable code; the fixed
resolver implements the operators. Definitions and assignments remain ordinary
event-log data.

Workshop rankings are `LabelSet` and `LabelCleared` events with structured values
(D13); see [workshop rankings](20.5-workshop-rankings.md).

## Organiser constraints

Organiser judgement uses the same label mechanism as family preferences. A board
drag creates a custom constraint; clearing its label is the undo operation.

### `LabelSet` for organiser decisions

The organiser board emits `LabelSet` events using a `ConstraintDefined` operator.
Exact room placement, co-assignment, separation, and other judgement all use the
same stable entity references and remain visible in the event history.

## Publication

### `PlanPublished`
```ts
{
  code_revision: string, config_hash: string, output_hash: string,
  notify: boolean, note: string | null
}
```

The one event about plans, and it records the decision that the plan derived from
events before this event is what families are being told. Its own `seq` identifies
the preceding plan's `input_seq`.

`output_hash` is the plan the organiser reviewed. It is checked on append: the server
derives at the position the event would occupy and refuses if the hashes differ,
which means the log moved while the organiser was reading. A board apply guards itself
the same way, on the position its pending events were composed against; publication
guards on the plan itself, because that is what the organiser actually read. Either way
the guard is what makes a sequence number on the payload unnecessary — you publish
the log as it stands, or you review it again.

The latest `PlanPublished` is the active publication; an earlier one is superseded by
a later one. If `notify`, the diff between the old published plan and the new plan is
computed and change emails are queued.

*Note:* the hash is computed by the server, but the actor is the organiser who published.
Publishing is the decision; the hash is what they decided about.

## What is deliberately not an event

Worth writing down, because the boundary blurs under pressure.

| Not an event | Why | Where it lives |
|---|---|---|
| Occasion-profile changes (adding, removing or reweighting a tag) | Code, versioned with the deployment; covered by `config_hash` | `profiles/<occasion>.ts` |
| Magic link issued / redeemed | Operational secret handling | `magic_link` |
| Session created / destroyed | Operational | `session` |
| Email sent, delivered, bounced | Operational telemetry | `email_log` |
| Page views, login times | Telemetry | Workers analytics, or nowhere |
| Entities, labels, and definitions as read models | Derivation, not decision | nowhere |
| Workshop auto-cancelled for under-subscription | Derivation; re-derives next run | plan trace |
| Party formation results | Derivation | plan trace |
| A plan, whether published or still being reviewed | Derivation; `derive()` reproduces it from its events and `input_seq` | nowhere |
| Pending events on an organiser's board | Not yet decided; discarding one must leave no trace | that organiser's browser |

The test: **would replaying the log without this produce a different plan?** If
no, it is not an event. Party formation is derived from labels and constraints,
both of which *are* events; the formation itself is not. A plan fails the same test
for every input sequence, including the one published, which is why publication does
not create a second plan type. What publication records is the decision and a hash of
the plan the organiser saw when making it.

Pending events are the interesting case, because they are events in every respect
except that nobody has committed to them. Applying them appends them here through
the ordinary path — validated, authorised, and written in one `batch()` so the set
lands whole or not at all. Discarding them does nothing at all, which is the point.
