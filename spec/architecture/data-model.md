# Data model

This document defines the generic data model shared by occasion profiles. Concrete
traits, values, module selection, and occasion policies belong in the occasion profile;
they must not require new typed property columns or domain foreign keys.

The event table, its KDL development representation, and the operational tables
are implemented; see the [implemented write side and text fixtures](../../docs/architecture/data-model.md).
This document covers the remaining, still-outstanding layers of the model:
typed entity identity for module-owned kinds, generic labels, and capacity.

The model has three layers:

1. `event` is the only persisted domain table.
2. Typed entities in the derived world provide durable identity for families,
   people, rooms, beds, places, workshops, and slots.
3. Labels in the derived world carry every domain property and every domain
   relationship. The constraint resolver interprets them using fixed
   occasion configuration.

None of the derived layers is stored. `derive(events, config)` builds them in
memory for the events a reader may see ([architecture](overview.md)).
Operational tables for sessions and delivery sit beside the log and are never
domain state.

Entities deliberately contain identity and ordering only. They do not carry
domain properties or references expressing domain relationships. Typed identity
is useful for stable URLs, authentication lookup, and lifecycle; the resolver
remains the only authority for what an entity means or relates to.

Conventions:

- Ids are text, prefixed by entity kind (`fam_`, `per_`, and each module's prefixes,
  such as `rm_` and `ws_`), and generated by the caller before appending, except
  where a module derives them.
- Timestamps are ISO-8601 UTC strings. SQLite has no date type.
- Email identities are Unicode-NFC normalized, trimmed, and lowercased before
  storage or comparison; provider-specific dot and plus-address rules are not used.
- Label values are canonical JSON scalars or objects, validated by occasion config.
- `sort_key` is the deterministic ordering anchor for every solver input.

Labels are stored domain facts emitted by events. Traits are profile-defined
schemas and resolver metadata over those label keys; a fold emits labels and
never creates traits. Event and module contracts explicitly map payload fields to
label keys, so the data model does not infer a label key from a field name.

## 1. Typed entity identity

The generic `Entity` shape, the kernel's `family`/`person` kinds, and the
mechanism a selected module uses to contribute any other kind are implemented;
see [implemented typed entity identity](../../docs/architecture/data-model.md).

Not yet provided: named, typed per-kind accessors on the world (`world.rooms`,
`world.beds`, …) — only the generic `world.entities_by_kind['room']`-style
bucket exists today. A room-only occasion should eventually expose buildings,
rooms, beds, and places this way; a workshop-only occasion, slots and
workshops; without changing the core model.

## 2. Labels

Labels carry all properties, capabilities, preferences, and references to other
entities. A value that names another entity is still just a value; the resolver
validates it and decides whether the relationship applies.

```ts
type Label = {
  entity_id: string
  key: string
  value: Json               // canonical JSON scalar or object
  value_type: string
  strength: 'required' | 'preferred' | null
  note: string | null       // optional organiser context; excluded from solver input
  set_seq: number
  cleared_seq: number | null
}
```

The world exposes the latest uncleared value for each configured label, indexed
by entity and by key and value. Keeping `set_seq` and `cleared_seq` makes replay
and temporal derivation explicit; the event log remains canonical.

Setup-owned labels are replaced as a group by their full-restatement event.
Labels from other event families and ordinary `LabelSet` events are independent
and remain in the world. Semantic relationship labels such as `member-of` and
`located-in` are declared by the event or module mapping; they are not inferred
by application lookups over event payloads.

Notes remain in the derived organiser world for display. The label's `set_seq`
links to its event's existing author and timestamp; no decision entity or metadata
table is created. Neither notes nor display-only attribution affect assignment,
scoring, or the canonical solver-output hash used by regression tests.

Examples:

```text
person:123  role=<profile-defined role>
person:123  birthdate="YYYY-MM-DD"
person:123  <profile-defined property>=<value>
person:123  needs=<profile-defined capability>

room:456    <profile-defined property>=<value>
room:456    provides=<profile-defined capability>

bed:789     <profile-defined bed property>=<value>
place:abc   <profile-defined place property>=<value>
```

Relationships such as a person's family, a room's building, a bed's room, and a
workshop's slot are labels as well. For example:

```text
person:123  member-of=fam_27
room:456    located-in=bld_3
bed:789     located-in=rm_456
place:abc   located-in=bed_789
workshop:9  offered-in=slot_sat-morning
```

These labels do not become lookups owned by application code. The resolver
checks entity kinds, cardinality, ownership, and validity when it resolves them.

## 3. Capacity and ordered choices

Capacity is represented by entities and labels, not special property columns: a
place is the atomic sleeping position, located in a bed, located in a room
([room inventory](../modules/room-inventory.md) §4). Ordered preferences are structured
label values validated by the `ordered-choice` operator
([workshop rankings](../modules/workshop-rankings.md) §6), which keeps the core model
generic while preserving that an ordered preference is not an unordered set.
