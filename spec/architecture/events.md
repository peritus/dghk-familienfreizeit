# Event model

This document defines the generic event envelope and lifecycle. Occasion profiles
may contribute event types through selected modules, but the append, replay,
validation, and fold rules are shared by every deployment.

This file lists the kernel write vocabulary. Modules contribute further event types,
each specified in its module document and registered by `defineModule`
([modules](../modules/contract.md) §3.1). Adding a kernel event type means adding to this file,
to `src/events/types.ts`, and to the fold; adding a module event type means adding to
the module specification and the module's `events.ts`. Nothing else.

Semantic setup events (`FamilyInvited`, `PersonAdded`, module events such as
`RoomAdded`) are convenient command vocabulary. Their complete payloads are
folded into one typed entity identity and generic labels. Constraints and
intrinsic facts then use the same `LabelSet` stream; no event type exists solely
for a particular preference or organiser decision.

## Shape

```ts
type Event<T extends string, P> = {
  seq: number            // head + 1 at append; the primary key rejects a stale append
  at: string             // ISO-8601 UTC, assigned at append time
  actor: Actor
  type: T
  subject: string | null
  payload: P
}

type Actor = string      // the authenticated principal, always
```

## KDL event-log format

Development and test event logs may be authored as KDL documents. Each
top-level node represents one event: its name is the event type and its
properties are the payload fields.

```kdl
FamilyInvited family_id=fam_a email="family_a@example.com" display_name="The A's" locale="de"
PersonAdded person_id=per_peter family_id=fam_a given_name="Peter" family_name="A" birthdate=#null role=adult
```

The project accepts a restricted KDL profile: one event node per line, no
positional arguments, and no child blocks. Blank lines and comments are allowed.
The parser reports syntax errors with file and line locations, rejects duplicate
properties, and maps only known event properties. Semantic validation then uses
the ordinary event payload schemas and replay invariants; KDL does not define a
new event vocabulary.

For ordinary authored fixtures, the loader supplies deterministic envelope
metadata: file order becomes `seq`, `actor` is `fixture`, `at` is a fixed test
timestamp, and `subject` is null unless a fixture explicitly supplies it. Tests
that exercise historical ordering or envelope behavior may provide `seq`, `at`,
`actor`, and `subject` as reserved properties. The loader must reject conflicting
or duplicate envelope fields.

KDL is the canonical authored representation for development and test event
logs. JSON may still represent API messages, serialized event rows, canonical
hash inputs, and derived results.

Every payload has a zod schema in `src/events/types.ts`. The schema is used twice:
to validate on append, and to validate on replay. Validating on replay sounds
redundant and is not — it catches the case where a schema changed and old events
no longer parse, which is the moment you need to write a migration rather than
discover the problem in the solver.

## Rules for payloads

1. **Payloads carry values, not references to mutable state.** `PersonAdded`
   carries the birthdate. It does not carry "look up the birthdate from the
   import file". Replaying the log must not require anything but the log.

2. **Payloads are complete, not deltas.** `PersonUpdated` and ranked-preference
   events carry complete restatements. Deltas mean the
   fold has to merge, merging has ordering subtleties, and the audit trail
   becomes unreadable. A full restatement is a few extra bytes and total clarity.

3. **Ids are generated by the caller before appending**, so the payload can
   contain them and the fold never has to invent one.

4. **No event ever contains a secret.** No tokens, no hashes of tokens, no
   session ids.

Setup event payloads are complete command inputs, not a second data model. Each
event or module declares an explicit fold mapping for its fields. A mapping marks
each field as identity-only or assigns its canonical stored label key; there is
no implicit payload-field-to-label conversion rule. The same mapping is used when
appending and replaying. Occasion-specific config defines which resulting labels
are legal and how the resolver uses them.

For a full restatement, a null field means that its mapped label is absent and
an omitted field is valid only when the event schema explicitly permits omission.
An update replaces the complete set of labels owned by that event family rather
than merging with the previous payload. Labels from other event families and
ordinary `LabelSet` events are preserved. Historical aliases normalize to the
canonical label key before ownership, cardinality, and resolver validation; an
alias must not collide with a canonical key or another alias.

The kernel mappings are:

| Event | Identity-only fields | Explicit label mappings | Other behavior |
|---|---|---|---|
| `FamilyInvited` | `family_id` | `display_name` → `display-name`; `email` → `email`; `locale` → `locale` | creates the family |
| `FamilyEmailChanged` | `family_id` | `new_email` → `email` | `old_email` is history-only; replaces the current email label |
| `PersonAdded` | `person_id` | `family_id` → `member-of`; `given_name` → `given-name`; `family_name` → `family-name`; `birthdate` → `birthdate`; `role` → `role` | creates the person |
| `PersonUpdated` | `person_id` | the same mappings as `PersonAdded` | full replacement of setup-owned person labels |
| `PersonWithdrawn` | `person_id` | none | `reason` is history-only; withdrawal is lifecycle state |

The `LabelSet` and `LabelCleared` payloads already carry their canonical `key`
explicitly and therefore do not use setup-event mappings. A profile trait may
describe any resulting label key, but the trait does not alter the event mapping.

Email addresses are values, not secrets, but their canonical form is part of the
event contract. `FamilyEmailChanged.old_email` and `new_email` are canonicalized
before validation, and replay rejects historical rows that do not satisfy the
canonical form rather than silently changing their identity.

## Setup and identity

### `FamilyInvited`
```ts
{ family_id: string, email: string, display_name: string, locale: 'de' | 'en' }
```
Emitted by an organiser, once per family, during import or manual add. Creates the
family. Does not send the email — that is an operational side effect performed
after the append succeeds.

*Invariant:* email must be unique case-insensitively across all families and
must not be an allowlisted organiser address. Checked against the derived world
before append; the `seq` guard makes the check and the append atomic. The import
preview reports a duplicate as a row-level error rather than aborting the whole
import.

### `FamilyEmailChanged`
```ts
{ family_id: string, old_email: string, new_email: string }
```
Organiser only. Carries the old value so the history reads correctly without
replaying to that point.

*Consequence:* the old address stops resolving to this family on the next request,
so its sessions lose access without a cleanup step
([authentication](../application/authentication.md) §3, rule 8).

### `PersonAdded`
```ts
{
  person_id: string, family_id: string,
  given_name: string, family_name: string,
  birthdate: string | null,
  role: string                  // values are validated by the active profile
}
```
Emitted by the family or by an allowlisted organiser, on the family's behalf
(D24). Folds to `member-of`, `given-name`, `family-name`, `birthdate`, and
`role`. Everything else about a person — bed demand, accessibility, diet — is
an ordinary label set by the module or profile trait that owns it.

*Note on `role`:* it is stated, not derived from birthdate. A 17-year-old may be
registered as an adult by their family and that is their call. Modules use `role`
for role-based rules; no module turns role into a bed exception.

### `PersonUpdated`
```ts
{ person_id: string, /* full restatement of all mutable fields */ }
```
Emitted by the family for its own people, or by an allowlisted organiser on
the family's behalf (D24).

### `PersonWithdrawn`
```ts
{ person_id: string, reason: string | null }
```
Excludes the person from newly derived plans. Historical plans keep them.
Emitted by the family for its own people, or by an allowlisted organiser on
the family's behalf (D24).

## Module events

Selected modules contribute these event types. Their payloads, invariants, and
authorisation are specified in the module documents.

| Module | Event types |
|---|---|
| [room inventory](../modules/room-inventory.md) §5 | `BuildingAdded`, `BuildingUpdated`, `RoomAdded`, `RoomUpdated`, `BedAdded`, `BedUpdated`, `BedRemoved` |
| [workshop space](../modules/workshop-space.md) §5 | `WorkshopSpaceAdded`, `WorkshopSpaceUpdated`, `WorkshopSpaceRetired` |
| [official workshops](../modules/official-workshops.md) | Official session content, eligibility, cancellation, and leader facts |
| [materials](../modules/materials.md) §5 | `MaterialRequested`, `MaterialRequestUpdated`, `MaterialRequestCancelled`, `MaterialCommitted`, `MaterialCommitmentUpdated`, `MaterialCommitmentWithdrawn`, `MaterialFulfilmentAdded`, `MaterialFulfilmentRemoved` |

Workshop rankings, food preferences, and organiser decisions add no event types;
they are `LabelSet` and `LabelCleared` events.

## Labels and constraints

Families may set labels only on themselves or their own people, through permitted
family-facing controls. Organisers may set labels through fixed resolver mechanisms
and profile/module vocabulary. Matching values may be free-form where the fixed
mechanism permits them. Kernel and module keys reserved for setup events remain
protected. The resolver validates scopes, values, strengths, and references before
append ([labels and constraints](labels-and-constraints.md) §4).

Profile deadline status is advisory and is not re-evaluated during replay or used to
reject an otherwise authorised event. A late event is part of the current log just
like any other event; release control determines whether it is included in a later
published plan.

### `LabelSet`
```ts
{
  entity_id: string
  key: string
  value: Json               // canonical scalar or structured resolver value
  strength: 'required' | 'preferred' | null
  note: string | null       // optional organiser context; ignored by the solver
}
```

This is the one event for intrinsic facts, preferences, capabilities, and organiser
decisions. Values may be scalar facts, free-form matching tokens, stable entity
ids, or structured values such as workshop rankings. For example:

```ts
{ entity_id: 'fam_42', key: 'needs', value: 'naehe_zum_eingang', strength: 'required', note: 'Nähe zum barrierefreien Eingang.' }
{ entity_id: 'rm_07', key: 'provides', value: 'naehe_zum_eingang', strength: null, note: null }
```

Profile-backed requirements use their explicit trait key and the canonical value
defined by the profile mapping. For example, the active profile writes
`key=needs-accessible value=accessible`; the resolver uses the trait's
`satisfied_by: 'accessible'` metadata and does not rewrite this as
`key=needs value=accessible`.

Omitting the optional note is equivalent to `note: null`, including when replaying
events and loading fixtures. Family-facing controls cannot set organiser notes.

Organiser decision labels may use every existing fixed resolver mechanism, including
`needs`, `provides`, `excludes`, separation, and workshop eligibility. The resolver interprets the value according to that
mechanism; the note is context for organisers and never changes the derived plan.

### `LabelCleared`
```ts
{ entity_id: string, key: string, value: Json | null }
```

`value: null` clears every current value for the key; otherwise the canonical value
identifies the application to clear. The original label event remains in the log.

Workshop rankings are `LabelSet` and `LabelCleared` events with structured values
(D13); see [workshop rankings](../modules/workshop-rankings.md).

## Organiser decisions

Organiser judgement uses the same label mechanism as family preferences. A board
drag or other organiser action creates one or more pending label events. Undo
removes that action's events from the local pending list; after application,
clearing a label appends `LabelCleared`. Organiser decisions are ordinary event-log
inputs and the solver derives the resulting assignment.

### Shared organiser context

Applied decision labels, their optional notes, event authors, and timestamps are
visible to every organiser in the event history and organiser views. Pending labels
remain local to the organiser's browser until applied.

---

## Communication

`Communicated` is the kernel event for an organiser's release decision. Its payload,
review identity, scope dependencies and authorisation are defined in
[release control](../application/release-control.md) §3. Its envelope supplies actor, time and
sequence; it stores no plan or arrangement snapshot. Previewing creates no event.

## What is deliberately not an event

Worth writing down, because the boundary blurs under pressure.

| Not an event | Why | Where it lives |
|---|---|---|
| Occasion-profile changes (adding, removing or reweighting a trait) | Code, identified by `build_revision` | `profiles/<occasion>.ts` |
| Magic link issued / redeemed | Operational secret handling | `magic_link` |
| Session created / destroyed | Operational | `session` |
| Email sent, delivered, bounced | Operational telemetry | `email_log` |
| Page views, login times | Telemetry | Workers analytics, or nowhere |
| Entities and labels as read models | Derivation, not decision | nowhere |
| Family placement units | Derivation | room-assignment plan section |
| A plan, whether communicated or still being reviewed | Derivation; `derive()` reproduces it from its events and `input_seq` | nowhere |
| Pending events on an organiser's board | Not yet decided; discarding one must leave no trace | that organiser's browser |

The test is whether this records an authoritative domain fact or organiser decision,
or merely a reproducible result. Family labels, material commitments and communication
decisions are events even when they do not change solver output. Assignments and
summaries are derived results. Communication records its reviewed `input_seq`, scopes and
`build_revision` and `compatibility_revision` under [release control](../application/release-control.md), never a plan
payload or an additional content hash.

Pending events are the interesting case, because they are events in every respect
except that nobody has committed to them. Applying them appends them here through
the ordinary path — validated, authorised, and written in one `batch()` so the set
lands whole or not at all. Discarding them does nothing at all, which is the point.
