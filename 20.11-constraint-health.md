# 20.11 — Constraint health

Module id `constraint-health` · factory `constraintHealth`

## 1. Purpose and boundary

Constraint health tells organisers which constraints are doing work, which are
redundant, and which cannot apply, and keeps a regression corpus of the constraints
organisers needed. The constraint mechanism itself — definitions, operators, labels,
validation, preflight — is kernel ([labels and constraints](04-labels-and-constraints.md));
this module adds the counterfactual analysis and the learning loop on top of it.

When an organiser knows something the solver does not, they add a human-readable
matching constraint:

```text
per_42 needs    room-with-garden-view
rm_07  provides room-with-garden-view
```

The resolver joins the labels and the solver treats the result like any other
required or preferred constraint. The event log records who added it and when; the
definition's description records why. There is no override model beside the
matching vocabulary (D6, D7).

## 2. Dependencies

Requires: none. Enhances: none. Its findings cover whatever solver modules are
selected.

## 3. Parameters

```ts
type ConstraintHealthParams = {
  counterfactual_limit: number       // most constraints analysed per dashboard load
  corpus_path: string                // regression corpus location in the repository
}
```

| Parameter | Default | Validation |
|---|---|---|
| `counterfactual_limit` | `200` | integer ≥ 1 |
| `corpus_path` | `'test/fixtures/constraints'` | relative path |

When active constraints exceed `counterfactual_limit`, the dashboard analyses the
most recent ones by `seq` and says how many it skipped.

## 10. Output and diff

Health is computed from the current world on every dashboard load, never
maintained:

```ts
type ConstraintHealth = {
  without_provider: readonly string[]        // required constraints nothing can satisfy
  contradictory: readonly string[][]         // sets of constraint keys that cannot all hold
  dangling: readonly string[]                // name withdrawn, retired, or absent entities
  effective: readonly { constraint_key: string, moves: readonly Change[] }[]
  redundant: readonly string[]               // can be cleared without changing the plan
  skipped: number
}
```

`effective` and `redundant` are one question asked twice, and it is a
counterfactual:

```
diff(derive(events ∖ c), derive(events))
```

Empty means `c` does no work and can be cleared; non-empty names exactly who moves
when it is removed. This needs no bookkeeping of its own, which is why it can be
recomputed on every load.

Clearing a constraint leaves its `LabelSet` event in history, and deriving at an
earlier `input_seq` reproduces the plan it produced.

## 12. Tests

### Regression corpus

A corpus fixture records a log position, the constraint labels, the expected
assignment, and the definition description — the same counterfactual the dashboard
runs, pinned so it can be asserted ([testing](14-testing.md) §5):

- a cleared constraint whose rule is now built in must stay satisfied without it;
  losing it again breaks the build;
- active constraints are informational and show the backlog; when one starts
  passing without its constraint, CI says so;
- a changed constraint or solver result produces a readable plan diff.

### Module tests

- `redundant` is empty for a constraint that moves anyone.
- Health is identical for any input order of events with equal `seq` positions.

## 13. When not selected

The dashboard health block, "safe to clear", and the regression corpus are absent.
Constraints still work and preflight still reports missing providers and
contradictions.
