# 20.5 — Room assignment

Module id `room-assignment` · factory `roomAssignment`

## 1. Purpose and boundary

Room assignment places parties into rooms and places. It owns hard room rules, soft
scoring, organiser placement constraints, forced placements, the sorted greedy pass,
bounded repair, unplaceable reporting, and the board. It consumes parties from
[sleeping parties](20.3-sleeping-parties.md), children's-room placements from
[child rooms](20.4-child-rooms.md) when selected, and distances from
[room adjacency](20.2-room-adjacency.md) when selected.

The method is a documented sort order, a scored greedy pass, and capped pairwise
swaps (D4), because organisers must be able to review why a party got a room. The
general determinism contract, rule interface, and trace format are in the
[solver contract](05-solver-contract.md).

This document is the authoritative description of room placement, room scoring,
and the room section of a plan.

## 2. Dependencies

Requires: [`sleeping-parties`](20.3-sleeping-parties.md).
Enhances: [`child-rooms`](20.4-child-rooms.md),
[`room-adjacency`](20.2-room-adjacency.md).

## 3. Parameters

```ts
type RoomAssignmentParams = {
  weights: {
    exact_fit: number                // bed_demand equals free places
    near_fit: number                 // leaves 2 or more free places
    orphan_bed: number               // leaves exactly 1 free place
  }
  keep_apart_tag: string | null      // relation tag that separates entities across rooms
  priority_tag: string | null        // requirement whose holders are placed first
  scarce_capabilities: Readonly<Record<string, number>>  // capability → penalty when used without need
  max_repair_passes: number
}
```

| Parameter | Default | Validation |
|---|---|---|
| `weights.exact_fit` | `10` | integer |
| `weights.near_fit` | `4` | integer |
| `weights.orphan_bed` | `-8` | integer ≤ 0 |
| `keep_apart_tag` | `null` | fills the keep-apart role (§6) |
| `priority_tag` | `null` | a `requirement` tag scoped to `person` or `family` |
| `scarce_capabilities` | `{}` | keys are capability tags scoped to `room`; values are integers ≤ 0 |
| `max_repair_passes` | `5` | integer ≥ 0 |

Defaults are starting values. Expect to tune them against an exported event log
with `npm run tune` ([deployment](13-deployment.md), weight tuning) and to deploy
each change as a profile change, never as an event (D12).

## 5. Events

None of its own. Organiser decisions on the board are ordinary constraints added
with `LabelSet` (D6); see §7, phase 0.

## 6. Labels and tag roles

Module-owned label keys: none.

| Role | Parameter | Required tag shape |
|---|---|---|
| Keep apart | `keep_apart_tag` | `relation`, operator `separates-from`, scopes `family` or `person`, symmetry `implied-mutual`, strengths `required` and `preferred` |

Room assignment also interprets, without a role parameter:

- every `requirement` tag that party formation lifted into `party.requirements`;
- the co-room relation named by `sleeping-parties`, for its soft terms;
- every active custom `needs-provides` constraint whose provider is a room or place.

## 7. Solver input and stages

Reads `rooms` and `places` from room inventory, `parties` from
`sleeping-parties.form`, placements from `child-rooms.place`, and adjacency when
selected. Rooms designated `staff`, `blocked`, or `child` are not candidates for
parties; `child` rooms and their places are pre-occupied by child placements.

### Stage `room-assignment.place`

`after: ['sleeping-parties.form']` · `reads: ['sleeping-parties.form', 'child-rooms.place']`

#### Phase 0 — organiser constraints

For each active required custom constraint that names a room or place, in `seq`
order then constraint key:

1. Resolve the constraint's people to parties.
2. If they span more than one party, record a conflict, skip it, and trace it. Do
   not attempt a partial placement. This happens when a constraint was created and
   party formation later changed under it; the organiser needs to know.
3. If the room lacks enough free places, record a conflict, skip, and trace.
4. Otherwise place the party and mark it placed.

A plan with unresolved conflicts is computed but needs an explicit acknowledgement
to publish.

#### Phase 1 — forced placements, to fixpoint

```
repeat:
  changed = false
  for each unplaced party, in party order:
    feasible = rooms where every hard rule passes
                       and free places ≥ party.bed_demand
    if feasible is empty: continue           // phase 4
    if feasible has one room:
      place it; changed = true
      trace "forced — only feasible room"
until not changed, or iterations > party count
```

The cap guarantees termination: each pass places at least one party or stops.
Forced placements carry no score and need no justification, which shortens the list
of decisions an organiser has to read.

#### Phase 2 — sorted greedy

Sort remaining parties by:

1. holds `priority_tag` at `required`, first — the hardest constraint, placed while
   options remain;
2. feasible room count, ascending — most constrained first;
3. `bed_demand`, descending — big parties before small ones;
4. lowest member `family_id`, ascending;
5. `key`, ascending.

```
for each party in that order:
  candidates = feasible rooms
  scored     = candidates.map(room => ({ room, score: score(party, room, ctx) }))
  best       = argmax(scored, tiebreak: room.sort_key asc, then room.id asc)
  place(party, best.room)
  trace(party, best, runners_up = next two by score)
```

Scoring is recomputed for every party, because an exact fit is only an exact fit
against the current free places.

#### Phase 3 — bounded repair

```
for pass in 1..max_repair_passes:
  improved = false
  for i in 0..n-2:                 // placed parties, fixed order
    for j in i+1..n-1:
      if swapping i and j is feasible for both
         and total score after > total score before:
           apply; trace; improved = true
  if not improved: break
```

Deterministic scan order, strict improvement only, hard cap. Swaps only — a swap is
one sentence in a trace; a three-cycle needs a diagram. If plan quality ever
demands more, add three-cycles as a separately labelled step.

#### Phase 4 — the unplaceable

For each unplaced party, evaluate every room and report the most common blocking
rule and the closest near-miss — the room failing the fewest hard rules:

> `P14` (Braun ×5, requires ensuite) — unplaced.
> 38 rooms rejected on capacity (needs 5 places, largest free is 4).
> 2 rooms rejected on ensuite.
> Closest: Room 31 (5 places free, no ensuite). Relaxing the ensuite requirement
> would place this party.

That last sentence is the product. An organiser either calls the family or adds a
constraint for Room 31.

#### Places within a room

A placed party takes the room's free places in place order, keeping members of one
family on adjacent places, and a two-place bed is filled by two members of the same
family before any other bed. Place-targeted constraints apply first.

## 8. Rules and scoring

Hard rules prune a room. They are not worth points.

| Rule id | Fails when |
|---|---|
| `hard.capacity` | free places < `party.bed_demand` |
| `hard.designation` | the room is not `general` |
| `hard.tag-requirements` | a `required` party requirement is not satisfied |
| `hard.keep-apart` | the room holds a party the candidate is kept apart from at `required` |

A requirement is satisfied in one of two ways:

- **`satisfied_by: '<capability>'`** — the room holds that capability. A set lookup.
- **`structural: '<check>'`** — a named check over the placement, provided by this
  module. `no-other-parties` passes when every current occupant belongs to this
  party, which no capability can express.

```ts
export const tagRequirements: Rule = {
  id: 'hard.tag-requirements',

  evaluate(party, room, ctx) {
    const missing = unsatisfied(party, room, ctx, 'required')
    return missing.length ? infeasible(missing) : 0
  },

  describe(party, room, ctx) {
    const missing = unsatisfied(party, room, ctx, 'required')
    return missing.length
      ? `${roomLabel(room)} fehlt: ${missing.map(tag => ctx.copy.tag(tag)).join(', ')}`
      : null
  },
}
```

Soft rules return integer score terms:

| Rule id | Term |
|---|---|
| `soft.exact-fit` | `weights.exact_fit` when `bed_demand` equals free places |
| `soft.near-fit` | `weights.near_fit` when 2 or more places remain |
| `soft.orphan-bed` | `weights.orphan_bed` when exactly 1 place remains |
| `soft.tag-preferences` | per `preferred` requirement: the tag's `weight` when satisfied, its `penalty` when not |
| `soft.co-room` | per unmerged co-room relation: the tag's `one_sided_weight` when both parties share the room; with `room-adjacency`, `adjacent_weight × (4 − distance) / 3`, rounded toward zero, otherwise |
| `soft.keep-apart` | per `preferred` keep-apart relation: the tag's `penalty` when violated |
| `soft.scarce-capability` | for each capability in `scarce_capabilities` the room holds and no member requires: its penalty |

`exact_fit`, `near_fit`, and `orphan_bed` are geometry: how well a party fits the
remaining places, whichever tags are involved. Every tag-specific amount lives on
its tag ([occasion profiles](16-occasion-profiles.md) §3).

**`orphan_bed` is a penalty, not a missing bonus.** A room left with one free place
is nearly always wasted, since most remaining parties have two or more people. It is
the term most worth tuning first.

**Scarce capabilities cost a little.** Using an accessible room for a party that does
not need it is not wrong, only wasteful when alternatives exist; a small penalty
says "prefer not to, but do it rather than leave someone unplaced".

**A preferred `no-other-parties` requirement is large and negative but not a hard
rule.** That is the point of the strength scale: `required` prunes, `preferred`
costs points. If the plan is tight the solver shares the room, the trace says so,
and an organiser can make a phone call.

## 9. Preflight checks

| Id | Severity | Fires when |
|---|---|---|
| `room-assignment.requirement-without-provider` | error | a requirement is `required` by at least one entity and no candidate room satisfies it |
| `room-assignment.requirement-arithmetic` | error | for a requirement, or the intersection of two requirements co-occurring on one party, required bed demand exceeds the places of satisfying rooms |
| `room-assignment.too-many-single-parties` | warning | one-person parties exceed `sleeping-parties.size_one_warning_threshold` |

Requirement arithmetic is the check to build first:

```
for each requirement tag R:
  demand = Σ bed_demand of parties requiring R at required
  supply = Σ places in candidate rooms satisfying R
  if demand > supply: error
```

> **needs-private-sanitary** — 19 beds required, 14 available.
> Five people cannot be placed regardless of how the rooms are arranged.
> Families affected: Braun (5), Weber (4), Koch (2), Lang (3), Ott (5).

That is a phone call, not a re-solve, and the earlier it appears the cheaper it is.

## 10. Output and diff

Plan section `room-assignment`:

```ts
type RoomAssignmentSection = {
  assignments: readonly {
    party_key: string | null           // null for a child-room placement
    person_id: string
    place_id: string
    room_id: string
  }[]                                  // sort: room order, place order
  unplaced: readonly {
    party_key: string
    reason: string
    near_miss: { room_id: string, failed_rules: readonly string[] } | null
  }[]
  conflicts: readonly { constraint_key: string, reason: string }[]
  stats: {
    parties_placed: number
    places_used: number
    places_free: number
    orphan_beds: number
    repair_passes: number
    repair_cap_hit: boolean
    total_score: number
    co_room_wishes_satisfied: number
    co_room_wishes_total: number
    unsatisfied_requirements: number
  }
}
```

`derive` asserts that no person and no place appears twice before returning a world.
`orphan_beds` and `co_room_wishes_satisfied` of `co_room_wishes_total` are the two
numbers that best express plan quality to a non-technical organiser.

A rendered greedy trace entry:

> **Room 14** (Haus B, 5 places, ensuite) ← **P07** (Müller ×2, Schmidt ×3).
> Score **22** — exact fit +10, ensuite preferred +6, co-room wish +6.
> Runner-up: Room 09, score 11 (no ensuite, leaves 1 orphan bed).
> Rejected: Room 22 — capacity (4 places, needs 5).

Every number traces to a named weight in the stored configuration, so an organiser
who disagrees can point at the term rather than the outcome.

`diff` change kinds: `room-changed` and `place-changed`, per person, attributed to
the person's family.

## 12. Tests

- Shuffle invariance over the whole room pipeline.
- One fixture per hard rule, and one where phase 0 reports a spanning conflict.
- Phase 1 reaches a fixpoint within the iteration cap.
- Phase 3 never accepts a non-improving swap and reports `repair_cap_hit`.
- Phase 4 names the closest near-miss.
- Requirement arithmetic message asserted verbatim.
- `movedCount` stays small when one constraint is added ([testing](14-testing.md) §7).

## 13. When not selected

No placement runs and the plan has no room section. The board, the room part of the
plan diff and family assignment page, and the accommodation reports are absent.
Parties may still be reviewed if `sleeping-parties` is selected.

## Known sharp edges

**Fragmentation from children's rooms.** A family of two whose child sleeps in a
children's room leaves a party of one. Several of those fill the plan with parties
that waste beds. The orphan-bed penalty helps; the real fix is party review, where
one-person parties are listed and organisers can merge them or talk to the families.

**Constraint conflicts after party changes.** A constraint created when Jonas was in
his family's party may span parties once he moves to a children's room. Phase 0
reports the conflict; it does not guess.

**Weight tuning is a live wire.** Changing a weight re-solves everything and can
move dozens of families. The dashboard refuses to publish a plan whose
`config_hash` differs from the previous publication without an explicit "I have
reviewed the diff" confirmation.

**Capacity exactly equal to demand.** Almost every soft term becomes irrelevant and
the solver degenerates into finding any feasible packing. The trace shows
`repair_cap_hit: true` with little improvement, and that is the honest report.

**Requirement inflation through merges.** A merged party inherits the strictest
strength of every requirement, so one family's `required` binds everyone sharing the
room. It is correct and surprising; party review shows who contributed it.
