# Workshop companion requests

This idea is accepted but deferred, outside the active roadmap. Promotion
requires explicit user scope approval, review of affected binding decisions,
and reinsertion into an active roadmap milestone under the
[deferred-scope policy](README.md).

If companion requests are considered later, they should be made in the context
of a specific workshop choice. A family member could name other people in the
same family they hope to attend that workshop with. The request would belong to
that workshop choice and current choice cycle; it would not be a general
person-to-person preference that applies across workshops.

No assignment guarantee or solver effect is defined here. Any future behavior
must preserve [D31](../../decisions.md#d31--automatic-workshop-attendance-is-limited-to-chosen-workshops):
a companion request cannot authorize automatic attendance at a workshop that a
person did not choose. Whether a request can affect allocation when all named
people independently chose the same workshop remains open.

## Open questions

- Is the request attached to a ranked workshop choice, a sign-up, or another
  workshop-specific action?
- Is it a soft preference, a hard joint request, or information for organisers
  only? What happens when capacity or eligibility prevents the group attending
  together?
- Must each named person make a matching request, or can one person's request
  express a one-way preference?
- Can a request name multiple family members, and how should partial fulfilment
  be represented and explained?
- How do edits, withdrawals, late workshop changes, and a new choice cycle
  affect existing requests?
